# api-access Specification

## Purpose
Who may call the API and at what rate: client apps identify themselves with per-client API keys, and requests without a key are confined to a rate-limited, read-only playground.

## Requirements

### Requirement: Per-client API keys
Each client app SHALL have its own API key, presented on every request in the `X-API-Key` header. A key SHALL be a high-entropy secret generated by the API, shown in full only once when it is issued, and stored only as a hash together with the client's name. Keys SHALL be issued, listed and revoked by an operator command, without a code change or a redeploy. A client SHALL have at most one active key at a time, except during a rotation, when the old and the new key are both accepted until the old one is revoked.

#### Scenario: Issue a key for a new client
- **WHEN** an operator issues a key for a client named `dmbk-photo`
- **THEN** the full key is printed once, only its hash is stored, and requests carrying it are accepted as `dmbk-photo` with no restart

#### Scenario: Listing never reveals a key
- **WHEN** an operator lists the clients
- **THEN** each client's name, creation time, last-used time and revoked state are shown, and no key or hash is shown

#### Scenario: Rotation
- **WHEN** an operator issues a second key for an existing client and has not yet revoked the first
- **THEN** requests carrying either key are accepted as that client

#### Scenario: Revoked key stops working at once
- **WHEN** an operator revokes a client's key
- **THEN** the next request carrying that key is refused, with no restart

### Requirement: Request classification
Every request SHALL be classified before any resolver runs, as exactly one of:
- **client**: `X-API-Key` matches an active key.
- **playground**: no `X-API-Key` header, or an empty one.
- **refused**: `X-API-Key` is present but matches no active key, including a revoked key.

A refused request SHALL get a GraphQL error with code `UNAUTHENTICATED` and no data. The message SHALL be the same for an unknown key, a revoked key and a malformed key.

#### Scenario: Valid key
- **WHEN** a request carries an active client key
- **THEN** it runs with the full schema, and session auth applies as before

#### Scenario: Wrong key is refused, not downgraded
- **WHEN** a request carries an `X-API-Key` that matches no active key
- **THEN** it fails with `UNAUTHENTICATED` and runs no part of the operation

#### Scenario: Failures are indistinguishable
- **WHEN** one request carries a revoked key and another carries random text
- **THEN** both get the same error code and message

### Requirement: Playground tier
A playground request SHALL run as anonymous: any `Authorization` header SHALL be ignored, so the viewer is null and only public data is visible. It SHALL be limited to `query` operations. A `mutation` or `subscription` SHALL be refused with code `FORBIDDEN` before it runs. Introspection SHALL remain available. Operations SHALL be refused with `BAD_USER_INPUT` when they exceed a maximum selection depth or a maximum number of aliased or repeated root fields, both configurable. GraphiQL SHALL continue to be served at `/graphql`.

#### Scenario: Public read from the playground
- **WHEN** a request without a key queries `dmbkPhotos(first: 5)`
- **THEN** it returns the public photos

#### Scenario: Session ignored without a key
- **WHEN** a request without a key carries a valid admin session token and queries `viewer`
- **THEN** `viewer` is null, and admin-only fields resolve as they do for anonymous callers

#### Scenario: Mutation refused without a key
- **WHEN** a request without a key sends any mutation, including `signInWithGoogle`
- **THEN** it fails with `FORBIDDEN`, and nothing is written

#### Scenario: Deep or fanned-out query refused
- **WHEN** a request without a key sends a query deeper than the configured depth, or one that aliases a root field more times than allowed
- **THEN** it fails with `BAD_USER_INPUT` before any resolver runs

#### Scenario: Introspection works
- **WHEN** GraphiQL loads without a key
- **THEN** its introspection query succeeds and the schema docs render

### Requirement: Playground rate limit
Playground requests SHALL be rate-limited per client IP, which is taken from the address the reverse proxy forwards. The window and request count SHALL be configurable. Over the limit, the request SHALL get HTTP 429 with a `Retry-After` header and a GraphQL error with code `RATE_LIMITED`, and SHALL run no resolver. Client-keyed requests SHALL NOT count against or be limited by the playground limit.

#### Scenario: Limit reached
- **WHEN** one IP sends more playground requests within the window than the configured limit
- **THEN** the excess requests get 429, `Retry-After`, and `RATE_LIMITED`

#### Scenario: IPs are limited separately
- **WHEN** one IP has exhausted its playground budget
- **THEN** a playground request from another IP still succeeds

#### Scenario: Clients are not limited by the playground
- **WHEN** a client-keyed request comes from an IP whose playground budget is exhausted
- **THEN** it runs normally

### Requirement: Enforcement rollout flag
Key enforcement SHALL be controlled by a setting that is off unless explicitly turned on. While it is off, a request without a key SHALL run as before this change, with sessions honoured, mutations allowed and no playground limits, and the server SHALL log that the request was keyless so remaining callers can be found. A request with an invalid key SHALL be refused whether the flag is on or off.

#### Scenario: Flag off
- **WHEN** enforcement is off and a request without a key sends an authenticated mutation
- **THEN** it runs as it did before this change, and the keyless request is logged

#### Scenario: Flag on
- **WHEN** enforcement is on and the same request is sent
- **THEN** it is handled as a playground request and refused with `FORBIDDEN`

#### Scenario: Bad key refused while flag is off
- **WHEN** enforcement is off and a request carries an unknown key
- **THEN** it fails with `UNAUTHENTICATED`

### Requirement: Keys stay out of responses and logs
The API SHALL NOT echo a presented key in any response, error or log line. Logs and the request context SHALL identify a client by name only.

#### Scenario: Refused key not echoed
- **WHEN** a request with an unknown key is refused
- **THEN** neither the response nor the server log contains the key's value

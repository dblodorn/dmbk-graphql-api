# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev        # tsx watch --env-file=.env src/index.ts — GraphiQL at http://localhost:4000/graphql
npm run start      # same, no watch
npm run typecheck  # tsc --noEmit
npm run build      # also just tsc — tsconfig has noEmit: true, so nothing is emitted
npm run test:mutations  # end-to-end mutation checks against a running local server (see below)
```

- No unit tests and no linter; `npm run typecheck` (covers `src/` and `scripts/`) is the only automated check. It runs as a pre-commit hook (`.githooks/pre-commit`, wired up by the `prepare` script on `npm install`) and as the `typecheck` CI job on every PR and before every deploy.
- `scripts/test-mutations.ts` exercises auth, API access and every mutation against **live data** through a local server, restoring all it changes. It issues itself a `test-mutations` API key for the run and deletes it afterwards; the playground suite runs only when the server is started with `API_KEYS_ENFORCED=true`. Google ID tokens can't be scripted, so it creates `.invalid` test accounts and sessions directly in `dmbk-accounts` and deletes them afterwards. Run `-- --setup` once: it adds those emails to the *local* `ALLOWED_EMAILS` / `ADMIN_EMAILS` — never add them to production's. `-- --cleanup` removes fixtures and test accounts left by a crashed run. The Are.na suite runs only when the server is started with `ARENA_API_URL=http://localhost:4099`: the script serves a stub Are.na there.
- `npm run chime:collection` creates `dmbk-sound.chime_compositions` with its `$jsonSchema` validator and indexes (`-- --apply`), or reports what it would do. Re-run it after every catalog update (see **Chime compositions**). Updating an existing validator is a `collMod`, which needs `dbAdmin` on `dmbk-sound`. `-- --collection <name>` targets a throwaway copy for testing.
- `npm run vz:collection` does the same for `dmbk-sound.vz_voices` (`-- --apply`; see **VZ voices**), and `npm run dx7:collection` for `dmbk-sound.dx7_voices` (see **DX7 voices**). Both call `scripts/synth-voices-collection.ts`.
- The `graphql-api` Atlas user needs **both** `readWrite` (every save) and `dbAdmin` (the collection scripts) on `dmbk-sound`. When granting one, check the other is still there: on 2026-11-17 a `dbAdmin` grant replaced `readWrite` and chime saves failed until it was restored.
- `npm run move:sound-snapshots` copies the SoundCloud snapshot from `dmbk-photos` into `dmbk-sound` (`-- --apply`), then `-- --drop-source` drops the old collection once the copy is at least as new. Report-only by default, never regresses a newer copy, safe to re-run.
- `npm run api-client -- create <client> | list | revoke <client> [--key <keyId>]` issues, lists and revokes per-client API keys in `dmbk-accounts.api_clients`. A key is printed once at `create` and stored only as its SHA-256; changes apply on the next request, with no deploy.
- `npm run backfill:owner-id` fills `ownerId` on LoRA records from their old `walletAddress` (`-- --map <wallet>=<userId> --apply`). Report-only by default and safe to re-run.
- `npm run backfill:models` writes the legacy FLUX `trainerModel` / `generatorModel` onto LoRA records that predate them (`-- --apply`). Report-only by default and safe to re-run.
- Code always runs through `tsx` (dev, start, and PM2 via `ecosystem.config.cjs`, as `node --import tsx`); there is no compiled output. Prod runs `npm install --omit=dev`, so `tsx` must stay in `dependencies`, not `devDependencies`.
- `.env` is loaded by Node's `--env-file` everywhere (Node errors if the file is missing): in the npm scripts and in PM2's `interpreter_args`. PM2 has no `env_file` option of its own.
- Env (`src/env.ts`, validated at startup): `MONGODB_URI`, `DO_SPACES_CDN_URL`, `DO_SPACES_ENDPOINT` / `REGION` / `KEY` / `SECRET` / `BUCKET` (required; the Space shared with dmbk and lora-trainer); `BETTER_AUTH_SECRET`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` (required in production); `BETTER_AUTH_URL` (this API's public URL); `ALLOWED_EMAILS` (who may sign in; empty admits nobody); `ADMIN_EMAILS` (who may curate photos); `ALLOWED_ORIGINS` (CORS: comma-separated hosts that call this API from a browser, e.g. `dmbk.io,*.dmbk.io,localhost:3000`; `*.` matches subdomains, not the apex — `lib/hosts.ts`); `PHOTOS_DB_NAME` / `SOUND_DB_NAME` / `LORA_DB_NAME` / `ACCOUNTS_DB_NAME` (default `dmbk-photos` / `dmbk-sound` / `lora-trainer` / `dmbk-accounts`); `ARENA_API_URL` (default `https://api.are.na/v3`; the tests point it at their stub); `API_KEYS_ENFORCED` (`true` turns keyless requests into the playground; anything else leaves them as before, logged); `PLAYGROUND_RATE_LIMIT` / `PLAYGROUND_RATE_WINDOW_SECONDS` (default 30 per 60 s, per IP) and `PLAYGROUND_MAX_DEPTH` / `PLAYGROUND_MAX_ROOT_FIELDS` (default 10 / 5); `CHIME_SAVE_RATE_LIMIT` / `CHIME_SAVE_RATE_WINDOW_SECONDS` (default 10 per 3600 s, per visitor) and `CHIME_SAVE_DAILY_LIMIT` (default 500 per client); `VZ_WRITE_RATE_LIMIT` / `VZ_WRITE_RATE_WINDOW_SECONDS` (default 60 per 3600 s, per visitor) and `VZ_WRITE_DAILY_LIMIT` (default 2000 per client); `DX7_WRITE_RATE_LIMIT` / `DX7_WRITE_RATE_WINDOW_SECONDS` / `DX7_WRITE_DAILY_LIMIT` (same defaults, DX7 voices' own budgets); `JUNO60_WRITE_RATE_LIMIT` / `JUNO60_WRITE_RATE_WINDOW_SECONDS` / `JUNO60_WRITE_DAILY_LIMIT` (same defaults, Juno-60 patches' own); `HOST` (default `127.0.0.1` in production, `0.0.0.0` otherwise); `PORT`; `NODE_ENV`.

## Deployment

**Every push to `main` deploys to production.** `.github/workflows/deploy.yml` SSHes into a DigitalOcean droplet, hard-resets `/opt/graphql-api` to `origin/main`, runs `npm ci --omit=dev`, and `pm2 startOrRestart ecosystem.config.cjs --update-env` (starts it on a fresh box, re-reads the ecosystem file otherwise). The script runs under `set -euo pipefail` and fails the job if `localhost:4000` does not answer afterwards. It needs the `DROPLET_HOST` (public IP), `DROPLET_USER` and `DROPLET_SSH_KEY` repo secrets. The deploy job `needs` the `typecheck` job, so a push that fails typecheck never deploys. Caddy terminates TLS for `graphql.dmbk.network` and proxies to port 4000.

## What this is

A Relay GraphQL API (Pothos + Yoga + Mongoose) over databases on one Atlas cluster (`dmbk-world`). It owns all of them, and in `dmbk-sound` the `chime_compositions`, `vz_voices` and `dx7_voices` collections:

| DB | Collections served | Owning app |
|---|---|---|
| `dmbk-photos` | `photos`, `keywords` | **this API** since dmbk's reads moved here ([dblodorn/dmbk#37](https://github.com/dblodorn/dmbk/pull/37)); dmbk writes and reads nothing in it. `models/photos.ts` is the schema source of truth, and the indexes are listed below |
| `dmbk-sound` | `sound_snapshots` (read-only here), `chime_compositions`, `vz_voices`, `dx7_voices` | per collection: `sound_snapshots` is `dblodorn/dmbk`'s (`src/lib/soundcloud/build-playlists.ts` is the only writer); `chime_compositions` (`lib/chime/`, saved for windchime) `vz_voices` (`lib/vz/`, saved for vz10m) and `dx7_voices` (`lib/dx7/`, saved for dx7) are **this API**'s |
| `lora-trainer` | `lora_trainings`, `generated_images` | **this API** since lora-trainer's `adopt-relay-graphql-client` shipped ([dblodorn/lora-trainer#32](https://github.com/dblodorn/lora-trainer/pull/32)). lora-trainer reads through the API and writes through the `loraTrainer…` mutations (`lib/lora/repository.ts`); it has no database access. `models/lora.ts` is the schema source of truth, and the indexes are listed below |
| `dmbk-accounts` | `user`, `account`, `session`, `arena_profiles`, `api_clients` | **this API** (better-auth manages its three collections and their indexes; `lib/arena/profile.ts` owns `arena_profiles` and `lib/api-keys/store.ts` owns `api_clients`, each creating its one index) |

lora-trainer no longer touches Mongo: its Atlas user (`lora-trainer-app2`) was deleted on 2026-10-26, and `graphql-api` is the only user with access to `lora-trainer`. The one collection another app still writes is dmbk's `sound_snapshots`. Moves like these go **one capability at a time, only once the replacement here is live**. Accounts live here, in `dmbk-accounts`; both apps sign in through it (`openspec/specs/accounts-auth/`; history in `openspec/changes/archive/2026-10-21-google-accounts/`). Both apps have moved; their old SIWE collections (`user`/`session`/`account`/`verification`/`walletAddress`) were backed up and dropped on 2026-10-21.

## Architecture

ESM (`"type": "module"`, `NodeNext`): relative imports need `.js` extensions in `.ts` files.

**Layers.** `models/` (Mongoose schemas) → `lib/*/repository.ts` (every query and write; all visibility rules) → `schema/` (Pothos types and resolvers, thin). Resolvers never build Mongo filters themselves.

**Models mirror foreign documents exactly.** String `_id`s (UUIDs for photos, hex for LoRA records), ISO-8601 *strings* for dates, explicit `collection` names, `versionKey: false`, no Mongoose timestamps. `autoIndex`/`autoCreate` are off globally (`db/mongoose.ts`) because the owning apps manage indexes — never enable them. (`dmbk-accounts` is written by better-auth's own adapter, not Mongoose.) Both DBs share one connection via `useDb(..., { useCache: true })`. The `dmbk-photos` indexes are this API's to keep now that dmbk no longer runs its `ensureIndexes`. They exist already, so create or change them by hand (Atlas or a one-off script), never through Mongoose:
  - `photos`: `{ keywords: 1, status: 1, hidden: 1, createdAt: -1, _id: -1 }` for the keyword-filtered listing (multikey prefix, with the keyset sort served from the index), and `{ status: 1, hidden: 1, createdAt: -1, _id: -1 }` for the unfiltered one.
  - `keywords`: `{ count: -1, _id: 1 }` for the vocabulary order.
  - `chime_compositions`: `{ fingerprint: 1 }` **unique** (the duplicate rule, race-safe) and `{ hidden: 1, createdAt: -1, _id: -1 }` for the listing. Created by `npm run chime:collection`.
  - `vz_voices`: `{ creatorHash: 1, fingerprint: 1 }` **unique** (duplicates per device key), `{ hidden: 1, createdAt: -1, _id: -1 }` for the listing, `{ creatorHash: 1, hidden: 1, createdAt: -1, _id: -1 }` for one key's listing. Created by `npm run vz:collection`.
  - `dx7_voices`: the same three indexes. Created by `npm run dx7:collection`.
  - `lora_trainings`: `{ requestId: 1 }` **unique** (the only duplicate check `loraTrainerCreateTraining` makes), `{ status: 1, hidden: 1 }`, `{ createdAt: -1 }`, `{ ownerId: 1, hidden: 1 }`. `generated_images`: `{ loraTrainingId: 1 }`, `{ ownerId: 1, hidden: 1 }`, `{ createdAt: -1 }`. lora-trainer's `ensureIndexes` created these and still re-ensures them until it drops Mongo; after that they're this API's to keep by hand. Two leftovers also exist (checked 2026-10-23) and nothing needs them: `lora_trainings.status_1` (covered by `status_1_hidden_1`) and `generated_images.walletAddress_1` (pre-accounts).

**Visibility lives in the repositories, and the per-request loaders in `context.ts` are pre-scoped to the viewer.** Node lookups (`node(id)`) and nested fields load through those loaders, so a record the viewer may not see resolves to `null` — indistinguishable from nonexistent.
- Photos: public = `status: "ready"` and `hidden: false` (`PUBLIC_SCOPE`); admins (`ADMIN_EMAILS`) see everything. `dmbkPhotos(visibility, states)` with non-default values is *refused* for non-admins, not silently narrowed. `originalKey` is never exposed; URLs are `DO_SPACES_CDN_URL` + derivative key.
- LoRA: public trainings = `completed` and `hidden ≠ true`; public images = `hidden ≠ true`. Owner = the account named by the record's `ownerId`; a record without one has no owner (`scripts/backfill-owner-id.ts`). An image's owner is whoever generated it, not the LoRA's trainer. `walletAddress` is pre-accounts history: kept in the model, never exposed. `hidden` uses `$ne: true` because lora-trainer never backfilled it. Writes (`loraTrainerCreateTraining` / `SetTrainingAssets` / `CompleteTraining` / `RecordImages`) record what lora-trainer's fal.ai work produced; the fal.ai calls and Spaces uploads stay in lora-trainer. They need a session, use the same NOT_FOUND-vs-FORBIDDEN rule as the hide mutations, and check URLs in `lib/lora/urls.ts`: every URL `https`, and mirror fields (zip, mirrored source images, an image's `cdnUrl`) under `DO_SPACES_CDN_URL/lora-trainer/`. Image ids come from the client (`lib/lora/ids.ts` checks the format), since it keys the Spaces copy by id before recording. `recordImages` inserts its batch in a transaction, the only one in this codebase (Atlas is a replica set). `trainerModel` (trainings) and `generatorModel` (images, given once per batch) are the fal.ai endpoint ids lora-trainer called (`lib/lora/models.ts`). Their shape is checked, not their value, because lora-trainer decides which models it offers. An omitted input or a missing field means the pre-picker FLUX endpoints (`fal-ai/flux-lora-fast-training` / `fal-ai/flux-lora`), on write and on read.
- Privileged fields (`Photo.hidden/status/failureReason`, owner-only `hidden/trainingZipUrl`) use scope-auth with `unauthorizedResolver: () => null` — they resolve to null rather than erroring, so one fragment serves public and admin views.

**Uploads** (`lib/photos/upload.ts`, `lib/spaces/`, `lib/photos/images.ts`) are ported from dmbk's `reserveUpload` / `finalizeUpload` / `delete`; key layout, limits, derivative sizes and failure handling must stay identical while both apps write. Bytes go client → Space through a presigned PUT, never through the API. Finalize runs one photo at a time (an in-process queue, sharp at one thread with no cache) and its derivatives sequentially, unlike dmbk: the whole API shares one 2 GB droplet, and a 50 MB original's decode is large. Storage deletes take the exact keys recorded on the photo, never a prefix — the Space is shared with other apps.

**Keyword counts are shared state.** `lib/photos/keywords.ts` and the `isCounted` rule in `lib/photos/repository.ts` are ported verbatim from dmbk (`src/lib/photos/keywords.ts`, `repository.ts`). While both apps write, any change to normalization or count maintenance must be made in both repos.

**Auth.** better-auth (`auth/better-auth.ts`) with Google as the only provider and the `bearer` plugin (`requireSignature`), built lazily on the Mongoose client. Its HTTP routes are **not mounted**: the browser gets a Google ID token from Google Identity Services, `signInWithGoogle` trades it for a signed session token through `auth.api.signInSocial`, clients send it as `Authorization: Bearer`, the context resolves it with `auth.api.getSession`, and `signOut` revokes it. Sign-up is gated in a `user.create.before` hook (verified email on `ALLOWED_EMAILS`, `auth/allowlist.ts`); every request re-checks `ALLOWED_EMAILS` and derives `isAdmin` from `ADMIN_EMAILS`, so removing an address takes effect immediately. Every sign-in failure is the same generic `AuthError` (`UNAUTHENTICATED`); a bad or revoked token is anonymous, never an error. `Viewer` is `id email name image isAdmin`: `image` is the Google picture better-auth stored at sign-up (not refreshed on later sign-ins; Google's URLs refuse hotlinks that send a referrer, so clients load them with `referrerpolicy="no-referrer"`). Scopes: `signedIn`, `admin`.

**API access** (`lib/api-access/`, `lib/api-keys/`; `openspec/specs/api-access/`). Every client app has its own key, sent from its server as `X-API-Key` and never from a browser (CORS deliberately doesn't allow the header). A Yoga plugin classifies each request in `onRequest`, before parsing: a valid key is a **client** with the full API and session auth as usual; an unknown, revoked or malformed key is refused (401 `UNAUTHENTICATED`, one message for all) in every mode; a keyless request is the **playground** when `API_KEYS_ENFORCED=true`, or **legacy** (exactly as before, logged once an hour per caller as `[api-access] keyless request`) when it isn't. The playground runs as anonymous whatever its `Authorization` says, allows only queries, caps depth and root fields with validation rules added per request (Yoga's validation cache is keyed by rule names, so these never leak into keyed results), and is rate-limited per IP with in-memory token buckets (429 `RATE_LIMITED` + `Retry-After`). The IP is the rightmost `X-Forwarded-For` entry (Caddy's), trusted only from a loopback peer, which is why production binds to `127.0.0.1`. A failed key lookup is 503, never a downgrade.

**Are.na** (`lib/arena/`). Read **anonymously** from Are.na's v3 API (`ARENA_API_URL`): only public and closed channels are served, and `client.ts` drops anything `private` from every result, so that stays true if a token is ever added. An account saves its Are.na username with `arenaSetUser` (looked up on Are.na first, stored in `dmbk-accounts.arena_profiles`, one per account). It isn't proved to be theirs, since it only selects public data. `Viewer.arena.channels` merges the user's own channels (group-owned included) with every channel of their groups, de-duplicated, newest-updated first, capped at 1,000 and paginated in memory. A failing group is skipped. `arenaChannel(slug)` is public; its `images` page by Are.na page, with the page carried in the cursor. Errors: `ArenaNotFoundError` → `NOT_FOUND` (Are.na's 401/403/404 all mean "not there"), `RATE_LIMITED`, `UPSTREAM_ERROR`. The anonymous budget is 30 requests a minute per server IP. Are.na app tokens (`client_credentials`) get an empty 404 from every endpoint, so they can't raise it.

**Relay.** `Photo`, `LoraTraining`, `GeneratedImage`, `ChimeComposition`, `VzVoice`, `Dx7Voice` are `Node`s with Pothos global IDs (base64 `Type:id`). `SynthPatch` (`id name data`, implements `Node`) is the interface every external synth's patch type implements (`VzVoice` and `Dx7Voice`; the interface is in `schema/types/vz.ts`), so windchime fetches any synth's patch with `node(id) { ... on SynthPatch { name data } }`; a later synth's patch type must implement it too. Every synth's voice documents have the same fields, so each type's `isTypeOf` also checks `data.length` against its format. Connections are keyset-paginated on `(createdAt, _id)` newest-first (`lib/cursor.ts`, same cursor encoding as dmbk); forward-only — `last`/`before` are refused. Fields are non-null by default (`builder.ts`); opt into `nullable: true` where a value can be absent. Mutations are `relayMutationField`s (single `input`, payload with the changed node); they return the repository's result, not a loader read, since the loader may hold a pre-mutation copy. Root Query/Mutation fields and `Viewer` fields that touch a database are prefixed with its camelCase name — `dmbkPhotos…` / `dmbkSound…` / `loraTrainer…` — dropping words the prefix already says (`dmbkPhotos`, not `dmbkPhotosPhotos`; `dmbkSoundPlaylists`; `loraTrainerTrainings`). Are.na isn't one of these databases; its fields take an `arena…` prefix in the same spirit. Cross-cutting fields (`_health`, `node(s)`, `viewer`, `signInWithGoogle`, `signOut`), type names and fields nested in node types are unprefixed. Input/payload/connection type names derive from the field name, so they follow automatically.

**Schema registration is by side effect**: `index.ts` imports `schema/queries.js` and `schema/mutations.js`, which import the type modules, before `builder.toSchema()`. A new schema file must be reachable from those imports.

**Chime compositions** (`lib/chime/`; `openspec/specs/chime-compositions/`). windchime (chime.dmbk.io) saves compositions anonymously through `dmbkSoundSaveChimeComposition` and lists them with `dmbkSoundChimeCompositions`. A document stores no account, IP or client. Units are the integers windchime's share links use, defined once in `shape.ts`, which builds both the zod input check and the collection's `$jsonSchema` validator (strict level, error action), so MongoDB refuses what the API would. Scales and voices are checked against `catalog.json`, a copy of windchime's `pnpm catalog` output: append-only, like windchime's index rule. To update it: run `pnpm catalog` in windchime, replace `catalog.json`, re-run `npm run chime:collection -- --apply` (the scale and voice enums live in the validator, and changing it needs `dbAdmin`), then deploy. A unit's `instrument` (`chime` tube chime, `furin` furin bell) is optional (so is `patch`, below): it stays out of `UNIT_FIELDS` and the validator's `required`, units saved before it read as `chime`, and the fingerprint appends it only for non-`chime` units, so stored fingerprints never change. External synths are voices `x:<synth>` (`<synth>` = the engine package name without `@dblodorn/` and `-engine`, e.g. `x:casio-vz` for `@dblodorn/casio-vz-engine`), and only their units hold `patch`: the 24-hex `_id` of a patch in that synth's library (a `vz_voices` document for `x:casio-vz`), or null for the synth's INIT. zod refuses a patch on any other unit and normalizes (external units always hold `patch`, others never), the fingerprint appends `patch` after `instrument` only for `x:` units, and the API never checks the patch exists (windchime falls back to INIT). A future synth's library must be a collection here keyed by a 24-hex `_id`. Any new unit field must follow the same rule, and its validator update (`chime:collection -- --apply`) must run **before** the code deploys, since the current validator refuses fields it doesn't list. Titles are generated here (`title.ts`, seeded by the fingerprint), never taken from the client. A furin unit's key is its root note alone, and its default voice reads as FURIN. Saving identical units returns the stored composition with `created: false`. Saves need a client key even while enforcement is off, and are rate-limited per visitor (`X-End-User-IP`, which `lib/api-access/plugin.ts` reads only on client requests, keeps only if it's an IP, and never logs) and per client per day (`limits.ts`). Admins hide abuse with `dmbkSoundSetChimeCompositionHidden`; nothing deletes.

**VZ voices** (`lib/vz/`; `openspec/specs/vz-voices/`). vz10m (vz10m.dmbk.io) saves Casio VZ-1/VZ-10M voices anonymously. A voice is its 336 decoded SysEx data bytes, base64 (`shape.ts`); the API reads the name from bytes 322–333 and never takes one from the client, and never parses parameters, so vz10m's codec can change without touching stored voices. Ownership is a **device key**: a 43-character base64url secret the browser generates and sends as `creatorKey`. Only `sha256("vz-creator:" + key)` is stored (`creatorHash`); the key is never stored or logged. That key alone can update and delete its voices (another key → `FORBIDDEN`; missing or hidden → `NOT_FOUND`) and filter the listing with `dmbkSoundVzVoices(creatorKey)`; `VzVoice.yours(creatorKey)` marks a caller's own voices in the public list. Duplicates are per key (unique `creatorHash`+`fingerprint`): the same key saving the same bytes gets `created: false`. Update keeps `createdAt` (and so the voice's place in the list) and sets `updatedAt`. Names are checked with `obscenity` plus a pass joining spelled-out letters (`names.ts`) on save and update. Save, update and delete need a client key and share one budget per visitor and per client per day (`limits.ts`). Delete removes the document; admins can also hide with `dmbkSoundSetVzVoiceHidden`, which locks the creator out too. Banks are not stored here; vz10m keeps them on the device.

**Synth voices** (`lib/synth-voices/`, `models/synth-voice.ts`). VZ and DX7 voices are one plan with two formats. `voiceShape(format)` handles byte count, name offset and length, and the device-key salt; `voiceRepository(model, shape, NotFoundError)` and `writeBudget(limits)` do the rest. `names.ts` is the shared obscene-name check, whose whitelist covers every synth's real voice names. A synth's `lib/<synth>/` only instantiates them. A third synth adds `lib/<synth>/`, `models/<synth>.ts`, `schema/types/<synth>.ts` (implementing `SynthPatch`, with a `data.length` `isTypeOf`), its query, four mutations, loader, error, env budgets and collection script.

**DX7 voices** (`lib/dx7/`; `openspec/specs/dx7-voices/`). dx7 (dx7.dmbk.io) saves Yamaha DX7 voices anonymously, exactly on the VZ plan above. A voice is its 155 unpacked VCED bytes, base64 (208 characters, one `=`), with the name at bytes 145–154 (10 characters, so `search` takes at most 10). The salt is `dx7-creator`, budgets `DX7_WRITE_*`, and the fields are `dmbkSoundDx7Voices` plus `dmbkSoundSaveDx7Voice` / `UpdateDx7Voice` / `DeleteDx7Voice` / `SetDx7VoiceHidden`. Windchime reaches a DX7 patch through `SynthPatch` like a VZ one. **Banks** (`lib/dx7/banks.ts`, `dx7_banks`, created by `npm run dx7:banks-collection`): a name (1–20 characters) and exactly 32 slots of `dx7_voices` ids or null, like a cartridge, on the voices' plan (same device-key hash, duplicates per key, update, delete, hide, the same three indexes, the DX7 write budget); `dmbkSoundDx7Banks`, `dmbkSoundSaveDx7Bank` / `UpdateDx7Bank` / `DeleteDx7Bank` / `SetDx7BankHidden`, slots sent as `Dx7Voice` global IDs. A slot may name anyone's voice; a deleted or hidden one reads as null. **Factory voices**: `npm run dx7:import -- --apply --banks <files.syx…>` saves DX7 .syx voices under `DX7_IMPORT_KEY` (in `.env`) and each 32-voice file as a bank named after it; Yamaha's ROM1A–ROM4B cartridges (from Dave Benson's DX7 page) are in, as 242 voices and 8 banks.

**Juno-60 patches** (`lib/juno60/`; `openspec/specs/juno60-voices/`). juno60 (juno60.dmbk.io) saves Roland Juno-60 patches anonymously, exactly on the VZ plan above. A patch is the juno60 editor's 42 bytes in its own layout (the Juno-60 publishes no data format), base64 (56 characters, no padding), with the name at bytes 26–41 (16 characters, so `search` takes at most 16). The salt is `juno60-creator`, budgets `JUNO60_WRITE_*`, and the fields are `dmbkSoundJuno60Voices` plus `dmbkSoundSaveJuno60Voice` / `UpdateJuno60Voice` / `DeleteJuno60Voice` / `SetJuno60VoiceHidden`. `Juno60Voice` implements `SynthPatch`; the voice types are told apart by `data`'s length (448 VZ, 208 DX7, 56 Juno-60). No banks. **Arpeggio** (`lib/juno60/arpeggio.ts`): a patch may carry arpeggiator settings beside `data`, never inside it: `Juno60Voice.arpeggio` (`version`, `on`, `mode` `UP`/`DOWN`/`UP_DOWN`, `range` 1–3, `rate` 0–127; null = off), an optional `Juno60ArpeggioInput` on save and update (an update without it removes it). The default (off, UP, 1, 64) is stored as none. The shared repository keeps it as a `VoiceExtra`; the fingerprint is the bytes' hash when there are no extras (so stored fingerprints never change) and covers the extras otherwise. The validator allows the subdocument (`juno60:collection -- --apply` before deploying any change to it). **Factory patches**: `npm run juno60:import -- --apply <files.json…>` saves patches from juno60 editor `.json` files under `JUNO60_IMPORT_KEY` (in `.env`); Roland's 56 factory patches are `factory/roland-juno60-factory.json` in dblodorn/juno60.

**Errors.** Repositories throw domain errors (`InvalidInputError`, `*NotFoundError`, `ForbiddenError`, `AuthError`); `errors.ts#maskError` maps them to GraphQL `extensions.code`s and masks everything else. Add new domain error classes to its `CODES` table or they surface as "Unexpected error."
